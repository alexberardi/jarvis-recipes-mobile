# jarvis-recipes-mobile

Expo/React Native mobile app for recipe management, URL/image import, and AI-powered meal planning.

## Quick Reference

```bash
# Install
npm ci                   # CI uses `npm ci`; use it locally too so the lockfile is honoured

# Development
cp env.template .env     # Configure API URLs
npm start                # Expo dev server
npm run dev:ios          # Open simulator + run
npm run ios              # iOS simulator
npm run android          # Android emulator

# Checks (both are required CI gates — see .github/workflows/build-and-deploy.yml)
npx tsc --noEmit         # Type check
npm test                 # Jest
npm run test:watch       # Jest, watching
npm run test:coverage    # Jest + coverage report in coverage/
```

generated by `npx expo prebuild` / EAS from `app.config.js`.

## Tech Stack

- **Expo 54** + React Native 0.81 + React 19 + TypeScript
- **React Navigation 7** (bottom tabs + native stacks)
- **React Native Paper** (Material Design UI)
- **React Query 5** (data fetching, caching)
- **expo-secure-store** (OS keychain for JWTs)
- **expo-image-picker** (camera/gallery for recipe images)
- **react-native-webview** (URL extraction fallback)

## Key Features

- **Recipe Import**: Add recipes from URLs (AI extraction) or photos (OCR)
- **Manual Entry**: Full recipe editor
- **Meal Planning**: AI-powered plan generation from preferences + date range
- **Browse & Search**: Filter by tags, search by name
- **Async Processing**: Job polling for URL/image parsing

## Auth invariants

Read these before touching `src/auth/AuthContext.tsx` or `src/api/recipesApi.ts`.

- **Tokens live in the OS keychain, never AsyncStorage.** `services/tokenStorage.ts`
  writes both tokens via expo-secure-store as `WHEN_UNLOCKED_THIS_DEVICE_ONLY`.
  Only the non-secret user blob stays in AsyncStorage. These are jarvis-auth
  credentials — a leak is valid against the whole stack, not just recipes.
- **A one-time migration** moves tokens written by pre-keychain builds out of
  AsyncStorage on the first `getTokens()` and deletes the plaintext copies, so an
  already-logged-in user survives the upgrade. Do not remove it until every
  install has been through it.
- **Refresh is single-flight.** jarvis-auth rotates refresh tokens, so two
  concurrent refreshes race to spend the same token and the loser is rejected.
  Every refresh — the 401 retry, a manual call, AuthContext's 10-minute timer —
  goes through `refreshAuthToken()` in `api/recipesApi.ts`, which coalesces
  callers onto one in-flight request.
- **Only a 401 means "stale token".** A 403 is a permission denial and must not
  log anyone out. A forced logout happens only when the `/auth/refresh` call
  itself returns 401/403, or when there is no refresh token at all; a transient
  network/5xx failure keeps the session.
- **expo-secure-store is a native module.** Adding or moving it needs a fresh
  prebuild / EAS build — an OTA-only update onto an older binary cannot load it.

## Error handling

`src/components/ErrorBoundary.tsx` wraps the tree in `App.tsx`, inside
`SafeAreaProvider` but **outside** `ThemeProvider`, so a throw from the theme,
Paper, Query or Auth providers still renders the fallback instead of a white
screen. The fallback deliberately uses only plain RN primitives and hardcoded
colors — it must not depend on the layer that may have failed.

## Testing

```bash
npm test
npm run test:coverage
```

- `jest.config.js` sets `collectCoverageFrom: src/**` so the headline number
  covers the whole app, not just files a test happened to import.
- `coverageThreshold` is a **ratchet at the currently measured baseline**, not a
  target: it exists to stop coverage sliding. RULES.md sets the house target at
  80%; `src/api`, `src/auth` and the token/job services are already 90%+, and the
  gap is almost entirely the screen layer. Raise the threshold whenever a screen
  gains coverage — never lower it.
- `jest.setup.js` globally mocks AsyncStorage, Reanimated and expo-secure-store.
- Screens rendering with `useFocusEffect` need a real `NavigationContainer`
  wrapper, not just a mocked `navigation` prop.
- Paper's `TextInput` renders its `label` as a Text node inside the input, so
  screen tests reach fields via `getAllByText('Email')`, the same idiom
  jarvis-node-mobile uses.

## Environment

Create `.env` from `env.template`:
```bash
EXPO_PUBLIC_AUTH_API_BASE_URL=http://localhost:7701
EXPO_PUBLIC_RECIPES_API_BASE_URL=http://localhost:7030
```

`src/config/env.ts` falls back to those same localhost values when the vars are
unset. Store builds must have real values supplied as EAS environment variables
/ GitHub Environment secrets — `eas.json`'s `preview` and `production` profiles
reference them by `${...}` and will resolve empty otherwise.

## Deployment

**EAS build profiles** (`eas.json`): `development`, `preview_internal`,
`preview`, `production`.

**GitHub Actions** (`.github/workflows/build-and-deploy.yml`):

| Trigger | Gates | Profile | GitHub Environment |
|---|---|---|---|
| PR into `main` | typecheck + tests only, no build | — | — |
| Push to `main` | typecheck + tests | `preview` | `jarvis-mobile-staging` |
| Push of a `v*` tag | typecheck + tests | `production` | `jarvis-mobile-prod` |
| `workflow_dispatch` | typecheck + tests | chosen input | chosen input |

There is no `staging` branch and nothing is wired to one. Nothing reaches
TestFlight unless `npx tsc --noEmit` and the Jest suite both pass first.

`.github/dependabot.yml` watches npm and github-actions weekly. The Expo/React
Native native surface is pinned to the SDK and deliberately ignored — move those
with `npx expo install`, not Dependabot.

See `DEPLOYMENT.md` for the full guide.
