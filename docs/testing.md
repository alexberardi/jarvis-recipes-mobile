# Testing

Three layers, each answering a question the others can't.

| Where | Mounts | Fakes | Answers |
| --- | --- | --- | --- |
| `__tests__/services`, `__tests__/api`, `__tests__/auth` | nothing | axios | Does this function compute the right thing? |
| `__tests__/screens` | one screen | the service beneath it | Does this screen behave? |
| `__tests__/flows` | real navigators | **only HTTP** | Does the app work? |

Run them all with `npm test`; `npm run test:flows` runs just the flow layer.

## The flow layer

`__tests__/flows/*.flow.test.tsx` render real screens inside the real
navigators, wrapped in the same providers `App.tsx` uses, and drive them by
pressing what a person would press. The only seam is HTTP: `recipesRequest` and
the `authApi` axios instance are replaced (`__tests__/flows/fakeApi.ts`), so
every service, hook, screen and navigator above them runs for real.

That seam is deliberate. Mocking a service module hides the class of bug these
tests exist to catch — the request body being wrong. A staged recipe's UUID went
through `Number()` to `NaN`, `JSON.stringify` turned it into `null`, and the
server's `exclude_recipe_ids: List[int]` rejected the lot; from inside the screen
that is invisible, and with the service mocked there is no body to inspect.
`fakeApi` records each request with its body **JSON round-tripped**, exactly as
axios would send it, for the same reason.

The files:

| File | Covers |
| --- | --- |
| `auth.flow.test.tsx` | Landing → Login → the app; stored sessions; sign-out. Includes where the token pair is allowed to live. |
| `quickPlan.flow.test.tsx` | The default planner's wire contract: which slots are requested, which ids are excluded. |
| `advancedPlan.flow.test.tsx` | All five screens of the LLM planner: dates → config → generate → poll → results → save, plus re-roll, swap, modal legibility and every refusal path. |
| `recipes.flow.test.tsx` | The box, adding from a URL, and the import mailbox. |
| `savedPlans.flow.test.tsx` | The saved plan on the planner tab, the plan library, opening and deleting one. |
| `groceries.flow.test.tsx` | The shopping list, ticking items off, and the Walmart cart export. |
| `fullJourney.flow.test.tsx` | Sign in → browse → plan → re-roll → sign out, once, in one mounted app. |

### What they do not cover

Anything that needs **layout**. A test renderer has no geometry, so a label
truncated by a sibling button ("Your week" rendering as "Your") or a misaligned
progress screen is invisible here. Catching those needs a device or a screenshot
runner. Detox is not an option in this repo: `android/` is gitignored and
regenerated by `expo prebuild`, which would wipe its native config on every
rebuild. Maestro (YAML flows, no native config) is the natural next layer.

**Colour is not in that category.** The renderer has no pixels, but it does have
the resolved styles, and a contrast ratio is a number. The date picker was
styled with literals written for a dark theme — `rgba(255,255,255,0.9)` text on
`rgba(255,255,255,0.04)` — so under the light theme the whole month rendered
white-on-white: every date present, every date tappable, none of them legible.
The copy-settings modal on the next screen had the mirror version, near-black
text on a hardcoded `#1c1c1e` card.

`__tests__/screens/CalendarLegibility.test.tsx` checks every day cell in both
themes for a ≥3:1 ratio (the WCAG AA floor for large text and UI components) and
asserts each colour is a theme token rather than a literal;
`advancedPlan.flow.test.tsx` does the same for the modal at 4.5:1. Reach for this
pattern whenever a screen paints its own surface.

## Adding a flow test

```tsx
import { fireEvent, screen, waitFor } from '@testing-library/react-native';
import PlannerNavigator from '../../src/navigation/PlannerNavigator';
import { lastCallTo, renderInApp, resetApi, route } from './harness';

jest.mock('../../src/api/recipesApi', () => require('./fakeApi').recipesApiMock());
jest.mock('../../src/api/authApi', () => require('./fakeApi').authApiMock());

beforeEach(() => resetApi());

test('...', async () => {
  route('POST', '/meal-plans/random', { slots: [], incomplete: false });
  renderInApp(<PlannerNavigator />);           // add { withAuth: true } for a session
  fireEvent.press(await screen.findByText('Plan 7 meals'));
  await waitFor(() => expect(lastCallTo('POST', '/meal-plans/random')).toBeDefined());
});
```

- `route(method, pattern, responseOrFn)` — later registrations win, so a test can
  override the setup's route. Return `httpError(status, detail)` for a rejection.
- **Anchor a collection route.** A bare `'/planner/plans'` also matches
  `/planner/plans/2`, and since later registrations win, the collection will
  answer a request for a single item with an array. Use `/^\/planner\/plans$/`.
- An unrouted request throws by name. That is on purpose: a silent `undefined`
  surfaces later as an unrelated render failure and costs far more to trace.
- `resetApi()` clears routes, recorded calls **and** the process-lifetime recipe
  cache in `services/mealPlans`. Without that last one a title cached by an
  earlier test answers the next one's assertion with no request made at all.

### Timezones

The suite is pinned to **Europe/Berlin** in `jest.config.js`. This app has
produced three timezone bugs, and each one is invisible in a UTC or US-local run:
`new Date(y, m, d).toISOString()` only shifts the date **east** of UTC. Running
there makes the date surface as hostile as it is for half the world.

Setting `process.env.TZ` inside a test does **not** work — jest's sandbox ignores
it. An earlier version of the calendar test looped over four zones while silently
running all four in the machine's own, and proved nothing. If a test depends on
the zone, assert the zone first (`expect(new Date().getTimezoneOffset())
.toBeLessThan(0)`) so it fails loudly rather than passing vacuously.

### Two things that will trip you up

Paper's `Checkbox.Item` marks its label container
`importantForAccessibility="no-hide-descendants"`, so the meal names on the day
config screen are **not** findable by text. Use
`getByRole('checkbox', { name: 'dinner' })`.

Paper renders a `TextInput`'s `label` as a `Text` node inside the input, twice,
and headers repeat their screen's action label. `lastByText` from the harness
resolves both cases. `Appbar.Content` hides its title and subtitle the same way
`Checkbox.Item` hides its label — assert on something else, or give the element
its own `accessibilityLabel`.

## Keeping the tests honest

Coverage thresholds in `jest.config.js` are a ratchet: they are the numbers
currently measured, floored. Raise them when a screen gains coverage; never lower
them to make a build pass.

Coverage says which lines ran, not whether an assertion would notice them
changing. The flow suite was checked by mutation instead — eleven deliberate
defects introduced one at a time (drop the exclusion list, stop trimming the
email, send the staged UUID as `NaN`, put the token pair in AsyncStorage, clear
the mailbox's own error message, …), plus four more for the theming and date-key
bugs (restore the white-on-white cell, restore `toISOString`, restore the black
modal card). All fifteen were caught. If you weaken an
assertion, re-run that exercise rather than trusting the percentage.
